## 三、第二轮：双方辩论（关键共识）

- **视角优先级**：**架构合约（Codex）> 运行时风险（Gemini）**。理由：合约撒谎第一笔请求就崩；并发问题在单机单用户评测下能苟过去
- **Gemini 公开收回**："能用" → "风险高"
- **唯一分歧（关于 Self-Verifier）**：
  - Codex：用 LLM 校验 LLM 闭环无硬事实源 → 反对
  - Gemini：在 Personal Agent 语境下用户偏好就是 Ground Truth → 支持

| **G-H2** | High | `RepeatedFailureDetector` 生命周期 / 状态作用域未声明 | Agent Core 章节加 conv_id 分桶或每次 run() 新实例化铁律 + 雷区 H9 |

### 主审取舍说明：G-C1 的二次审议

**第一次决策**: 主审认为评审历史是"方法论沉淀"价值高，删除可惜，初判**未采纳** G-C1。

**主人复议**: "我发现 Gemini 说的 G-C1 问题的确应该采纳——元数据和版本更迭介绍部分的确很臃肿。追加修改的同时直接独立出去单独作一个文档。"

**最终决策**: 采纳 G-C1，但用"独立成档"替代"删除"——既消除主文档的认知噪音，又不丢失方法论价值：

- 主文档（`脚手架prompt_v3.md`）→ 纯执行指令集，给 Claude Code/Cursor 拿来跑
- 本档案（`评审历程档案.md`）→ 方法论沉淀，给人看（团队复盘、博客素材、面试谈资）

**学到的事**: 主审第一次直觉对了一半（"方法论沉淀有价值"），错了一半（"所以应该塞主文档"）。Gemini 的本质洞察是 **关注点分离**——脚手架 prompt 是给 LLM 执行的指令集，不是给人看的 portfolio。混在一起既稀释 LLM 注意力，又让人看着臃肿。最优解是**两份文档各司其职**。

## 八、Self-Verifier 三层方案的辩证演进

### 双方原始立场（第一轮）

| 立场 | Codex | Gemini |
|------|-------|--------|
| 论点 | 用 LLM 生成的记忆校验 LLM 答案 = **闭环无硬事实源** | Personal Agent 语境下**用户偏好就是 Ground Truth**，强求外部硬事实源是误判业务边界 |

### 折中方案（v3 起 — 三层校验）

- **Stage 1**：`tool_results` 硬规则（确定性，无 LLM）—— 满足 Codex 的"hard truth first"
- **Stage 2**：structured `profile.json` 一致性（确定性，无 LLM）—— 印证 Gemini 的"用户偏好即 Ground Truth"
- **Stage 3**：LLM 软兜底（带抽样路径）—— 处理非结构化长尾问题

### 五轮迭代关键改进

- v3：建立三层架构
- v3.1：Stage 2 改强校验（数字/日期/枚举/自由文本各自规则），废弃字符串包含；Stage 3 加抽样独立路径
- v3.2：Stage 3 强制 SDK Structured Outputs，禁止裸 prompt 解析

## 十、方法论沉淀

### 多 AI 评审的关键收益

1. **互补盲区**: Codex 偏架构、Gemini 偏运行时，单一评审者必有盲区
2. **零成本辩论**: 让两个 AI 互相质疑，比一个 AI 自我反思更深入
3. **共识 vs 分歧**: zero-disagreement 共识项必修；分歧项需主审仲裁
4. **演进式收敛**: 每轮评审揭示前一轮的盲点；分数从 v2 风险高 → v3.2 8.2-8.3 → 终态 9.0+

### 关注点分离（G-C1 教训）

主文档（给 LLM）和方法论文档（给人）必须**两份分离**：
- 给 LLM 执行的脚手架 prompt：纯指令、纯约束、零 meta-data
- 给人看的辩论档案：完整论点、修订对照、致谢

混在一起会两边都受伤——LLM 被噪音稀释注意力，人看到也觉得臃肿。

### 自然语言约束 > 示例代码

第四轮重写关键洞察："写得越多越容易在示例里再次犯错"。对 LLM 下达的指令集应该是：
- ✅ **行为契约**（"Detector 必须按 conv_id 隔离"）
- ✅ **反模式禁令**（"禁止在 __init__ 里全局实例化"）
- ❌ **完整代码示例**（容易引入新 bug 当样板）
