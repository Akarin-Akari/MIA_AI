  🎯 共识必修 5 项（按优先级排）

  1️⃣ C5: 内部 IR 字段改名 tool_use_id → tool_call_id

  - 两位都强调，证据一致
  - 位置: 第八章 CanonicalMessage 类型契约约 311-316 行
  - 理由: tool_use_id 是 Anthropic 术语泄漏到中立内部
  IR。这不是吹毛求疵——它会重新把实现者的脑回路带回"先按 Anthropic 想，再兼容
  OpenAI"的老坑（Codex 原话）
  - 改法: 字段名改 tool_call_id，第八章 / 第九章 Critical Rules /
  第十章雷区清单同步修改

  2️⃣ H5 重写（两位都激烈批评，Gemini 措辞最狠）

  - Gemini 原话: "纯属瞎扯！如果 Verifier 的核心职责是拦截幻觉并输出
  revised_answer，它必须在主链路里同步阻塞等待"
  - 现状错误: H5 "Self-Verifier 串行阻塞主响应" 把"verifier 阻塞"和"memory
  extraction 阻塞"混为一谈
  - 后果: Claude Code 会把 verifier 异步扔后台 → 毁掉拦截闭环
  - 改法: 拆成两条规则
    - ✅ Verifier 必须主链路阻塞（依赖 Stage 1/2 提速 + Stage 3 gating
  频率限制）
    - ❌ 禁止把 memory/fact extraction 挡在主响应前（应 fire-and-forget 异步）

  3️⃣ C7: Tier 2 持久化隔离域声明

  - 两位都列为 Critical
  - 现状: profile.json / learned_facts.md 是全局单文件
  - 后果: 如果启用 --api 模式被多端调用，所有人画像和记忆混写到同一个 
  JSON——Gemini 直接定性为"恐怖的 Data Bleed"
  - 改法: 二选一
    - 🔘 在第三章背景 + 第八章 Memory 明文声明 "Single-user 
  assumption"（推荐，60 分钟实战足够）
    - 🔘 改为 users/{user_id}/profile.json 作用域设计

  4️⃣ C6: 单轮多 tool_calls 契约 + 测试

  - 两位都列为 Critical
  - 现状: 第十一章 Acceptance 只覆盖单工具 roundtrip
  - 后果: "单工具调用能过，双工具调用乱套" 的假兼容（Codex 原话）
  - 改法: 第八章加 contract（按 id 回填、顺序保持）+ 第十一章
  test_provider_translation.py 加双 tool_calls 同轮返回用例

  5️⃣ C8: 并发锁测试盲点（Gemini 独家发现）

  - 现状: Acceptance 只验内存隔离，没要求并发文件写入测试
  - 后果: LLM 极易把 asyncio.Lock() 实例化在 Request Handler 内部 →
  局部锁防不住并发写穿 profile.json
  - 改法: Acceptance 加"并发请求并发写 profile.json，验证锁有效性"测试用例
